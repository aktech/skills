# Authoring Beautiful SVG Diagrams

Write architecture diagrams as hand-crafted SVG, not via mermaid/graphviz. The output is a single `.svg` file that drops into a PR description, blog post, or README. Style: dark background, one brand accent color, monospace labels, sparse strokes: visually similar to the OpenAI engineering blog diagrams.

## When to use

- A PR / blog post / README needs ONE high-quality diagram.
- The diagram has a few named entities and arrows between them: not 50 nodes, not generic flowcharts.
- The reader is technical; mono labels and short system-style box names are appropriate.
- You want it to look intentional, not autogenerated.

## When NOT to use

- 50+ nodes or auto-layout from data → use `graphviz` / `mermaid` / `d2`.
- The diagram needs to update from data (live status, generated topology) → use a tool that renders from data.
- The audience expects a marketing-glossy illustration: get a designer.

## Style baseline

| Element | Value |
|---|---|
| Background | `#000` or near-black (e.g. `#0A0410` for purple-tinted dark) |
| Primary text + frame strokes | `#F2E6FA` (warm cream/lavender) |
| Subtle text + dashed strokes | `#D8B4F0` (muted, ~70% lightness) |
| Component fill (dark) | `#5B0B6B` (deep brand color) |
| Highlight / special component | `#BA18DA` (full brand accent) |
| Stroke widths | 1 (frames), 1.25 (arrows), 1.5 (accent arrows), 0.75 (hairlines) |
| Corner radius | 3 (small tiles), 4 (output boxes), 6 (outer container) |
| Font | `ui-monospace, SFMono-Regular, Menlo, monospace` for everything |

Pick a brand accent color first. Examples: violet `#BA18DA`, OpenAI orange `#CC6F47`, Anthropic ochre `#D97757`. Build the dark, mid, light shades from that root: pick a deep version for fills, the original as the accent, and a desaturated light version for subtle strokes/text.

## Light "paper" theme (alternative baseline)

Validated on a production infrastructure diagram. Style of ML-paper
model-architecture figures (e.g. Higgs Audio): white canvas, soft pastel tiles, serif labels,
generous whitespace. Use when the doc it lands in is light-background, or the user points at a
minimal/paper-style reference.

| Element | Value |
|---|---|
| Background | `#FFFFFF` |
| Primary-role tile (the story's subject) | fill `#E9F6EC`, stroke `#43A047` 1.5 |
| Secondary-role tile (supporting services) | fill `#E8F1FC`, stroke `#6FA8DC` 1.5 |
| External-system tile | fill `#FFFFFF`, stroke `#909090` 1.25 |
| Grouping boundary | fill `#F6F6F6`, stroke `#ABABAB` 1.25, dash `5 4`; outermost boundary slightly lighter `#FCFCFC`, dash `6 5` |
| Tile corner radius | 10 (components), 9 (small token tiles), 12-16 (boundaries, larger = outer) |
| Component name | serif (`Charter, Georgia, serif`) bold 13.5, `#1A1A1A`, centered |
| Caption under name | same serif regular 11, `#7A7A7A` |
| Title | monospace bold ~23 (only the title + code-ish strings are mono: domains, bucket names, image tags) |
| Arrow labels | serif italic 11; colored to match arrow (`#2E7D32` on green, `#8A8A8A` on gray) |
| Boundary labels | serif 11-12 `#8A8A8A` |

Principles specific to this theme (beyond the shared layout rules):

- **Two arrow grammars, stated in the legend.** Color encodes *kind of flow*, e.g. green = the
  runtime/data path the diagram is about, gray = deploy/control plumbing. Solid = flow with an
  arrowhead and a job; short dashed gray lines = mere association ("this service manages that
  group"), no arrowhead needed.
- **Tile color encodes role, not layer.** Subject-of-the-story workloads get the accent (green),
  platform services get the quiet color (blue), things outside the system boundary get plain white. The
  legend then reads as three one-liners.
- **Token-row pattern for N-of-a-kind.** A horizontal row of small rounded squares (44px, one
  bold serif letter each) + `· · ·` ellipsis between the first ~5 and last ~4 reads instantly as
  "many identical workers". Caption the row with the cardinality (`n_workers per run (1-230)`).
  Far better than one box labeled "xN".
- **Group label placement:** outer boundaries label top-left inside the border; inner groupings
  (the "stage" the eye lands on last) label bottom-center, like a figure caption.
- **Legend top-left under the title** (not bottom): swatch + one short clause per row, ~5 rows max.
- **No decorative icons.** No logos, no wave glyphs, no clip-art people beyond a minimal
  circle+arc figure if a human actor matters. If an element doesn't carry information, delete it:
  the user WILL ask "what is this?" about anything ornamental.
- **Captions in plain English, not platform jargon.** "won't be stopped mid-run" beats
  "priority=critical · evict=false". Acronyms a reader must look up get
  translated or cut; exact identifiers (bucket names, image tags) stay verbatim in mono.
- **Trapezoid = transformer.** A wide-top trapezoid for the one thing that converts between
  domains (a build system, an encoder). At most one or two per canvas.

Class block for this theme:

```svg
<style>
  .bg{fill:#FFF}
  .title{fill:#1A1A1A;font-family:ui-monospace,SFMono-Regular,Menlo,monospace;font-weight:700}
  .mono{fill:#444;font-family:ui-monospace,SFMono-Regular,Menlo,monospace}
  .name{fill:#1A1A1A;font-family:Charter,Georgia,serif;font-weight:700}
  .cap{fill:#7A7A7A;font-family:Charter,Georgia,serif}
  .tile-green{fill:#E9F6EC;stroke:#43A047;stroke-width:1.5}
  .tile-blue{fill:#E8F1FC;stroke:#6FA8DC;stroke-width:1.5}
  .tile-ext{fill:#FFF;stroke:#909090;stroke-width:1.25}
  .boundary{fill:#FCFCFC;stroke:#9A9A9A;stroke-width:1.25;stroke-dasharray:6 5}
  .group{fill:#F6F6F6;stroke:#ABABAB;stroke-width:1.25;stroke-dasharray:5 4}
  .a-green{fill:none;stroke:#43A047;stroke-width:1.5}
  .a-gray{fill:none;stroke:#8A8A8A;stroke-width:1.25}
  .albl-g{fill:#2E7D32;font-family:Charter,Georgia,serif;font-style:italic}
  .albl-gr{fill:#8A8A8A;font-family:Charter,Georgia,serif;font-style:italic}
</style>
```

## Layout principles

- **One canvas. One story.** A diagram answers one question. If it answers two, split it.
- **Padding > density.** Aim for 30px gaps between major regions, 20px between elements inside a region. Cramped diagrams read as "draft."
- **Dashed = container; solid = thing.** Dashed strokes for system boundaries, environment boundaries, conceptual groupings. Solid filled rectangles for actual objects (services, workers, queues, storage).
- **Outline-only + dashed = logical/abstract.** When something isn't a real runtime object (e.g. a logical replica, a virtual volume, a future component), give it a translucent fill + dashed border to distinguish it from real components.
- **Color highlights one thing.** The bright accent should mark exactly one or two elements. The thing the diagram is *about*. Everything else is the dark variant.
- **Arrows have a job.** Each arrow is either data flow or a relationship. Don't draw arrows for visual filler.
- **Legend at the bottom.** Two lines, max. Explain only the things a literate reader can't infer (color meaning, special arrow types).

## CSS-style class block

Define classes once in `<style>`, reuse via `class=` attributes. Don't inline styles per element.

```svg
<style>
  .bg     { fill: #0A0410; }
  .frame-soft { fill: #F2E6FA; fill-opacity: 0.04; stroke: #F2E6FA; stroke-width: 1; }
  .zone   { fill: none; stroke: #D8B4F0; stroke-width: 1; stroke-dasharray: 4 3; }
  .comp-fill   { fill: #5B0B6B; }
  .comp-accent { fill: #BA18DA; }
  .label  { fill: #F2E6FA; font-family: ui-monospace, SFMono-Regular, Menlo, monospace; }
  .title  { fill: #F2E6FA; font-family: ui-monospace, SFMono-Regular, Menlo, monospace; font-weight: 600; }
  .sub    { fill: #D8B4F0; font-family: ui-monospace, SFMono-Regular, Menlo, monospace; }
  .arrow  { fill: none; stroke: #F2E6FA; stroke-width: 1.25; }
  .arrow-accent { fill: none; stroke: #BA18DA; stroke-width: 1.5; }
  .legend { fill: #D8B4F0; font-family: ui-monospace, SFMono-Regular, Menlo, monospace; font-size: 11px; }
  .out    { fill: #0A0410; stroke: #F2E6FA; stroke-width: 1; }
</style>
```

## Skeleton

```svg
<svg width="900" height="640" viewBox="0 0 900 640" fill="none" xmlns="http://www.w3.org/2000/svg">
  <style>...</style>
  <rect class="bg" width="900" height="640"/>

  <!-- Title block -->
  <text class="title" x="40" y="48" font-size="20">Diagram title</text>
  <text class="sub" x="40" y="70" font-size="13">One-line subtitle answering "what does this diagram show"</text>

  <!-- Outer container (e.g. the system boundary) -->
  <rect class="frame-soft" x="40" y="100" width="600" height="370" rx="6"/>
  <text class="legend" x="56" y="120">system</text>

  <!-- Inner zones (e.g. hosts or regions) -->
  <rect class="zone" x="60" y="140" width="180" height="310" rx="4"/>
  <text class="legend" x="72" y="158">zone 1</text>
  ...

  <!-- Components inside zones -->
  <g>
    <rect class="comp-fill" x="76" y="180" width="148" height="34" rx="3"/>
    <text class="label" x="88" y="201" font-size="11">component-name</text>
  </g>

  <!-- Highlighted component -->
  <g>
    <rect class="comp-accent" x="276" y="280" width="148" height="44" rx="3"/>
    <text class="label" x="288" y="299" font-size="13" fill="#000">special-thing</text>
    <text class="label" x="288" y="314" font-size="11" fill="#000">subtitle</text>
  </g>

  <!-- Logical/abstract object (replica, virtual resource) -->
  <rect x="76" y="490" width="148" height="26" rx="2"
        fill="#5B0B6B" fill-opacity="0.5"
        stroke="#D8B4F0" stroke-width="0.75" stroke-dasharray="3 2"/>
  <text class="label" x="92" y="507" font-size="11">logical thing · 10Gi</text>

  <!-- Output boxes ("what this produces") -->
  <g>
    <rect class="out" x="690" y="240" width="170" height="64" rx="4"/>
    <text class="label" x="704" y="262" font-size="13">Output</text>
    <text class="label" x="704" y="282" font-size="13" fill="#D8B4F0">name</text>
    <text class="legend" x="704" y="298">descriptor</text>
  </g>

  <!-- Arrows + markers -->
  <defs>
    <marker id="arrowhead" markerWidth="8" markerHeight="8" refX="7" refY="4"
            orient="auto" markerUnits="strokeWidth">
      <path d="M0 0 L7 4 L0 8 Z" fill="#F2E6FA"/>
    </marker>
    <marker id="arrowhead-accent" markerWidth="8" markerHeight="8" refX="7" refY="4"
            orient="auto" markerUnits="strokeWidth">
      <path d="M0 0 L7 4 L0 8 Z" fill="#BA18DA"/>
    </marker>
  </defs>

  <!-- Curved arrow from a real component into an output -->
  <path class="arrow" d="M604 363 C 660 363, 660 272, 690 272" marker-end="url(#arrowhead)"/>
  <path class="arrow-accent" d="M424 424 C 600 424, 620 352, 690 352" marker-end="url(#arrowhead-accent)"/>

  <!-- Legend at bottom (35px below the last frame) -->
  <g transform="translate(40, 585)">
    <text class="legend" x="0" y="0">extra clarification a reader can't infer (e.g. 'X hosts Y processes')</text>
  </g>
  <g transform="translate(40, 615)">
    <line x1="0" y1="0" x2="22" y2="0" class="arrow"/>
    <text class="legend" x="30" y="4">primary path</text>
    <line x1="160" y1="0" x2="182" y2="0" class="arrow-accent"/>
    <text class="legend" x="190" y="4">accent path</text>
  </g>
</svg>
```

## Padding rules of thumb

| Between | Pixels |
|---|---|
| Title block bottom → outer container top | 30 |
| Outer container bottom → first legend line | 35 |
| Legend line → next legend line | 30 |
| Legend → canvas bottom | 25 |
| Inner container top → first inner element | 40 (leaves room for the container's text label) |
| Two stacked components | 18-22 |
| Component to highlighted component | 22 |

If you ever feel "this looks cramped", the gap is probably <20px and you should grow it.

## Common mistakes

| Mistake | Fix |
|---|---|
| Long label overflows its tile | Shorten the label, OR widen the tile, OR shrink the font. Don't let text bleed outside the rect. |
| Two pieces of text occupy the same pixels | **No text may overlap any other text or sit on top of a filled tile that isn't its own.** This includes arrow labels crossing through component tiles, response/forward labels colliding mid-channel, and right-aligned labels sliding under right-side components. After placing every text element, mentally draw its bounding box (≈`fontSize * len * 0.6` wide, `fontSize * 1.2` tall) and check it against every other text bbox AND every filled rect on the canvas. If two arrows in opposite directions need labels in the same channel, stack the labels: one above the line, one below: or move the arrows to different y-rows so each label has its own clear strip. |
| Multiple things highlighted with the accent color | Highlights stop being highlights. Pick one. Move others to dark variant. |
| Arrows drawn from "the container's right edge" rather than from a specific component | Anchor each arrow to the component it represents (e.g. `scheduler` → output, not `system` → output). Otherwise the legend can't explain what the arrow means. |
| Logical/abstract things drawn identically to real components | Use translucent fill + dashed border for logical (virtual, future, conceptual). Solid fill for real components. |
| Mixing fonts for "code-y" text and "prose" text | Pick one font (monospace works for both because it's neutral). The diagram should look like one thing, not a slide deck. |
| Arrows without markers | Use `marker-end="url(#arrowhead)"`. Don't draw triangles by hand. |
| viewBox dimensions don't match width/height | Set both to the same numbers. Mismatch causes scaling surprises. |
| Forgetting the canvas-fill `<rect>` | The SVG itself has no background; the first `<rect>` defines the dark canvas. Without it, the diagram inherits whatever background it's embedded in (often white) and unreadable. |

## Iteration loop

1. Draft the layout in your head: outer container, inner zones, components, arrows, output region, legend.
2. Write the SVG.
3. `open file.svg` (macOS) or load in browser.
4. Look for: overflow, missing padding, ambiguous arrows, accent overuse, label truncation. Fix.
5. Show to the human. Expect feedback. Common iterations:
   - "X is missing" → add it without disturbing existing layout (grow the canvas if needed; don't compress).
   - "Y looks wrong" → either rename or restructure; don't paper over with annotations.
   - "Padding feels off" → check the padding table above and adjust.
6. Final pass: re-read every label aloud. Anything ambiguous or wrong gets rewritten.

## Anchoring arrows

Arrows are the diagram's grammar. Each one says "X relates to Y in this way." Two rules:

1. **Arrows must start at a specific component**, not at a container's edge. If the arrow starts at "the system", the reader doesn't know which component owns the relationship.
2. **Curved arrows beat straight lines** when crossing layout regions. Use `path d="M sx sy C cx1 cy1, cx2 cy2, ex ey"` cubic bezier with control points pulling the curve toward a smooth arc. Straight lines that pass through other shapes look like crossings, not connections.

Example: arrow from a tile at `x=276..424, y=402..446` to an output box at `x=690, y=320..384`:
```
<path class="arrow-accent"
      d="M424 424 C 600 424, 620 352, 690 352"
      marker-end="url(#arrowhead-accent)"/>
```
Source is the right edge midpoint of the tile (`424, 424`); target is the left edge midpoint of the output (`690, 352`); two control points pull the curve into a smooth S.

## Do not

- Use SVG filters / gradients / shadows. They make the diagram look 2010-era. Flat color, sharp edges, monospace.
- Embed raster images (PNG/JPEG `xlink:href`). The whole point of SVG is vector: keep it pure.
- Convert text to paths "for safety". You'll regret it the first time you fix a typo. Use real `<text>` and let the viewer's font stack handle it.
- Add a watermark, logo, or "Generated by ..." footer. The diagram speaks for itself.

## Output

Save to a descriptive file name for ad-hoc work, or commit alongside the doc that references it.

For PRs/READMEs that render the SVG inline, GitHub strips `<style>` blocks in some contexts. If the diagram needs to render in those, inline the styles per element. For everywhere else (Notion, Slack, Preview, browsers), keep the `<style>` block: much more maintainable.

## Convert to PNG

Some platforms (Slack, some GitHub contexts, Twitter) prefer raster.

**On macOS: first choice: headless Chrome. Do NOT use `rsvg-convert`.**

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu --screenshot=output.png \
  --window-size=1580,1000 --force-device-scale-factor=2 \
  "file:///path/to/input.svg"
```

Set `--window-size` to the SVG's exact width/height; `--force-device-scale-factor=2` doubles the pixel density for retina embeds. This is also the render-verify loop: screenshot → Read the PNG → fix → repeat.

`qlmanage -t -s 1800 -o /tmp input.svg` also renders with native Core Text fonts, BUT it has produced a **squashed square thumbnail** (a 1580x1000 SVG came out 2200x2200, aspect ratio destroyed, right side visually crushed). Verify the output dimensions with `sips -g pixelWidth -g pixelHeight` before trusting it; fall back to headless Chrome when the aspect is wrong.

`rsvg-convert` (Cairo/Pango) **drops the macOS-specific fonts**: it doesn't resolve `ui-monospace` or `SFMono-Regular` through Fontconfig and falls back to a generic monospace (DejaVu / Liberation), changing the diagram's look. Don't use it on macOS unless you've explicitly switched the SVG's font stack to a Fontconfig-known font like `Menlo` or a webfont with `@font-face`.

**On Linux / CI**: different problem: no SF Mono available regardless. Either:
- Switch the SVG to a font that's installed on the system (`DejaVu Sans Mono`, `JetBrains Mono`), or
- Embed a webfont via `<defs><style>@font-face{...}</style></defs>` and use a renderer that respects it (`resvg` or headless Chrome).

`-s 1800` is output longest-side in px. Bump to `2400+` for retina PR embeds. Avoid ImageMagick (`convert`) for SVG → PNG: text rendering is poor.
